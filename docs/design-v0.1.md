## 0. 一句话定义

**Clarify 是一个本地优先的极简待办软件：用一句话把脑子里的东西说进去，AI 自动把它变成排好期的待办，你只需要看和点完成。**

- 输入：全局快捷键 → 说一句（或打一句）→ 不打断当前工作
- 处理：本地 ASR → 本地 LLM → 结构化 JSON → 默认安排
- 输出：常驻悬浮窗永远只显示少数几件真正要做的事；完成 24h 后自动从视野消失
- 边界：无账号、无服务器、无遥测；音频默认不留存；数据只在本机

### 主张（Product Thesis）

1. **零决策捕捉**：捕捉路径上用户只做一个动作（说/写），其他都交给默认规则。
2. **清晰是规则不是感觉**：用一组可执行的"清晰规则"约束界面（见 §3.3），不是靠 UI 留白碰运气。
3. **AI 在前台隐身**：AI 不当聊天助手，只当"安静的记录员 + 排期员"；它永远不要求你确认。
4. **本地即信任**：断网可用、无登录、数据可导出、模型可替换。

### 明确不做（v1 范围外）

- 不做协作/共享清单、不做团队项目
- 不做日历双向同步（先本地提醒）
- 不做聊天式 AI 助手、不做 AI 自动执行操作
- 不做多端实时同步（schema 预留，后续可加"文件快照同步"）
- 不做 Kanban / 复杂项目层级 / 自定义字段

## 1. 关键洞察：把"零决策"拆成可实现的三条规则

"全程不让用户做第二项决策"是最大的体验承诺，也是最容易翻车的点。我建议把它拆成三条可验证的规则：

- **R1 创建零决策**：捕捉时永不弹确认框。AI 输出的默认值直接生效，但每个默认值都要**可被一键修正**（悬浮提示："我按 *明天 09:00* 安排了，点此修改"）。
- **R2 组织零决策**：不要求用户建清单/项目/标签。默认用"今天 / 以后 / 等待"三个系统视图组织；标签可选、可被语音自动识别（"#工作"）但不强制。
- **R3 清理零决策**：完成即从视线消失；24h 后自动软归档；30 天内可从"回收站"恢复。用户永远不需要做"要不要删"的决定。

> 核心张力：**解析不可能 100% 正确**。"零决策"不能等于"零纠错"。解法是——**不阻塞的纠错**：默认值可视化、单击可改、5 秒撤销、出错时原文永远保留。这比"创建前确认"体验好一个数量级，也更符合理念。

### 1.1 延迟悖论与"乐观 UI"

本地 LLM 在小机器上解析一句话需要 2~10 秒，用户不可能等。所以链路必须"**先接住，后变聪明**"：

1. 语音停止的瞬间，就用已转写的文本创建一条草稿卡（标题=原话，时间=无）→ **立即出现在悬浮窗**，给一个轻微的"接住了"动效。
2. 后台 ASR 出 final → LLM 解析 → **原地升级**该卡片（标题精炼、补时间、必要时拆成多条）。
3. 解析结果用一条可点击的轻提示告知（"已安排 · 明天 15:00 · 与张总开会"），**不弹窗、不阻塞**。
4. 任何一步失败 → 保留原文进收件箱，绝不丢输入。

这条设计决定了产品"感觉快"，而不是"实际快"。

## 2. 用户与场景（MVP 目标人群）

- **首要用户**：25~40 岁、知识工作者、Windows 笔记本、事情多且碎片化、用过滴答清单/Todoist 但坚持不下来（因为"整理成本 > 收益"）。
- **核心场景**：
  1. 开会/走路/写代码时突然想起一件事 → 快捷键说一句 → 继续手上的事（3 秒内回到原工作）。
  2. 坐在电脑前，悬浮窗就是"今天的台面" → 一眼看到 3~5 件事 → 点掉一件 → 它消失。
  3. 晚上打开主窗口，看今天完成了什么、清一下收件箱里 AI 没把握的几条。
- **次要场景**：单纯打个字建待办（不想说话）、推迟一件事、提醒到点弹通知。

## 3. 核心对象模型（最小化）

### 3.1 一个实体就够了：`tasks`

不要一开始做"清单/项目/看板"层级，那会把极简产品做成 Notion。v1 的数据模型：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | TEXT (uuid) | |
| title | TEXT | 精炼后的标题（解析后） |
| notes | TEXT NULL | 备注/原文补充 |
| status | TEXT | `inbox` / `active` / `done` / `archived` |
| due_kind | TEXT | `none` / `date`（全天）/ `datetime`（定时） |
| due_at | TEXT NULL | ISO8601 本地时间，`2026-11-02T15:00:00+08:00` |
| remind_at | TEXT NULL | 提醒时间（可早于 due，如提前 10 分钟） |
| recurrence | TEXT NULL | RRULE 子集，如 `FREQ=WEEKLY;INTERVAL=1;BYDAY=MO,WE` |
| tags | JSON | 可空数组，如 `["工作"]` |
| waiting_for | TEXT NULL | 等待他人时填人名（用标记而非状态，降低复杂度） |
| source | TEXT | `voice` / `text` / `quick` |
| raw_text | TEXT NULL | 原始口述，用于纠正/复盘 |
| parse_confidence | REAL | 0~1，低置信度进收件箱并打 ✨ 标记 |
| parse_meta | JSON NULL | 假设说明、置信度细节 |
| sort_order | REAL | 手动排序（v1 可只做默认排序） |
| created_at / updated_at / completed_at / archived_at | TEXT | |
| archived_reason | TEXT NULL | `done` / `dismissed` |
| device_id / schema_version | TEXT / INT | 为未来同步/迁移预留 |

**重复任务**：单独一张 `task_completions` 表（task_id, completed_at, due_at_snapshot）。重复任务"完成"不结束任务，而是写一条完成日志、把 `due_at` 推进到下一次；主界面"已完成 24h"视图展示的是完成日志。这样"今天跑完 3 公里"既有打卡记录，又不会在台面上留痕。

### 3.2 状态机

```
                    ┌─────────────┐
  语音/文字/快捷添加 → │   inbox     │  （未安排/待整理：无日期或低置信度）
                    └──────┬──────┘
         AI 解析出日期 / 手动排期 │
                           ▼
   ┌───────────────┐   ┌──────────┐  点击完成   ┌──────┐  24h 后   ┌──────────┐
   │   archived    │◄──│  active  │───────────►│ done │─────────►│ archived │
   │ (30 天后可删)  │   └──────────┘            └──────┘          │ (可恢复)  │
   └───────────────┘        │  ▲                   │              └──────────┘
                            │  └───────────────────┘ 撤销（5s 内 / 从完成列表恢复）
                            │  标记"等待他人"（waiting_for，不改变 status）
                            ▼
                        逾期 = 派生视图（due_at < now 且 status=active），不单独使用状态
```

- **逾期不是状态**：它是查询结果（`active` 且已过期），避免额外的状态流转。
- **删除**：先软删（`archived_reason=dismissed` + 30 天回收站），用户无需"确认删除"。
- **v1 只需 4 个状态**；"等待他人"用 `waiting_for` 标记即可，等真实需求出现再升级状态机。

### 3.3 清晰规则（Clarity Rules）

写进产品验收标准的硬规则：

1. 悬浮窗同时展示 **≤ 5 项**（超出折叠成"+3 项"）。
2. 完成项 **立即**从悬浮窗消失；主窗口"已完成"保留 24h 后清空。
3. 无日期事项只进 **收件箱**，不占悬浮窗（除非用户选择"收件箱"视图）。
4. 每项默认 **单行**：复选框 + 标题 + 时间（时间用弱化色）；详情 hover/点击展开。
5. 悬浮窗最多显示 **一个数字**（如逾期条数），不做多枚红色徽标（焦虑源）。
6. 空状态也是设计过的状态（"今天清空了 🎉" / "说一句试试"），不能是空白。
7. 主窗口"已完成"区明确显示"23h 后自动清除"，让"清空"可预期。

## 4. 关键链路（交互状态机）

### 4.1 捕捉链路（语音/文字二合一入口）

**入口设计建议**：一个热键（如 `Ctrl+Alt+Space`）唤出**迷你捕捉条**，默认自动开始听；下方同一条里可以直接打字；不说话时按 `Enter` 即发文字。用户不需要先选"语音还是文字"（少一次决策）。

```
空闲 ──热键──► 捕捉条出现（80ms 内）
                 │  自动开始录音 + 实时波形 + 流式字幕
                 │  用户可直接打字（覆盖语音）
                 ├─ Esc ──────────────► 取消（丢弃，不落库）
                 ├─ 静音 1.2s / 热键再按 / 松开 ──► 停止录音
                 ▼
            立即创建草稿卡（status=inbox，title=当前转写文本）
                 │  UI 给"接住了"反馈，悬浮窗刷新
                 ▼
            ASR final（<1s）→ 更新 raw_text
                 ▼
            LLM 解析（后台 2~8s）→ JSON → 原地升级/拆分任务
                 ▼
            轻提示："已安排 · 明天 15:00 · 与张总开会" [撤销]
```

要点：
- **按住说话 vs 按一下说**：建议默认"**按住说**"（拟对讲机、边界清晰、防误触），松开即结束；设置里可切换"按一下开始/再按结束"。
- **取消**：`Esc` 丢弃；如果已经转写出文字，取消后**保留草稿在收件箱**（不丢），或按设置决定。
- **最长 60s**、超时自动结束；连续重复按热键 1s 内视为同一次（去抖）。
- **失败兜底**：ASR 失败 → 提示"没听清，已保留文字，可编辑"；LLM 失败/超时（>8s）→ 原始文本作为收件箱任务，不重试打扰用户。
- **多件事**："明天下午三点跟张总开会，顺便买牛奶" → 拆 2 条，due 分别为明天 15:00 / 无（进收件箱），并汇总提示"创建了 2 项"。
- **乐观 UI 的视觉语法**：草稿卡有细微的"正在理解"呼吸/流光，解析完成后 150ms 变形——这是产品"AI 感"最关键的 2 秒。

### 4.2 完成链路

单击复选框 → 复选框打勾 + 标题划线（150ms）→ 从悬浮窗消失（300ms 淡出）→ 右下角 toast："完成 · 今天已完成 3 项" [撤销 5s]。
- 撤消：5s 内 toast / 主窗口"已完成"中点击恢复。
- 误点防护：复选框热区足够大即可，不需要二次确认（确认=增加决策）。
- 重复任务：完成后进度推进，toast 显示"下一次：周一 09:00"。

### 4.3 24h 清空链路

- 后台任务（每小时/启动时）扫描 `status=done AND completed_at < now-24h` → 设为 `archived`（软）；主窗口"已完成"只显示 24h 内。
- 已归档数据保留 30 天（回收站），之后物理清理；用户可导出。
- **不要硬删除**：24h 自动删除 = 一次误点就永久丢数据，违反"信任"。

### 4.4 提醒链路

- `remind_at` 到点 → Windows 原生通知（标题 + 完成/推迟按钮）→ 点击打开主窗口定位。
- 应用必须托盘常驻 + 开机自启；睡眠唤醒后补查错过的提醒，合并成"逾期 N 项"。
- ⚠️ 提醒的可靠性是本地应用的长期痛点（关机期间无法触发），需要在首次设置里说明预期。

### 4.5 悬浮窗编辑链路

主窗口 → 「悬浮窗」页 → **左侧实时预览**（真实渲染同款组件）+ 右侧配置 → 修改即时生效（无需保存按钮）→ 悬浮窗真实位置可用鼠标拖动，位置记忆。提供"恢复默认"。

## 5. 悬浮窗：显示方式规格

悬浮窗是产品的"脸"，建议 v1 **只做 2~3 种**，其余 v1.1 再做（模式越多越难做精）。

| # | 模式 | 内容 | 适用人群 | 默认尺寸 |
|---|---|---|---|---|
| 1 | **今日**（默认） | 逾期 + 今天共 ≤5 条，底部"＋" | 大多数人 | 260×?（自适应） |
| 2 | **下一条** | 只显示最该做的一条（逾期 > 今天定时 > 今天全天），大字号 + 大勾 | 极简/专注 | 220×80 |
| 3 | **收件箱** | 未安排事项 ≤5 条，可一键排"今天/明天" | 收集型用户 | 260×自适应 |
| 4 | 时间轴 | 今日剩余时间线（"10:00 周会"…） | 日程型用户 | v1.1 |
| 5 | 极简计数 | 一个圆点 + 数字（逾期/今日数），hover 展开 | 极致极简 | 56×56 |
| 6 | 自定义清单 | 某个标签/筛选 | v1.1+ | — |

**窗口行为**（全模式通用）：
- 无边框、圆角、半透明毛玻璃（Win11 Mica/Acrylic 降级为纯色）、可选置顶（默认开）、跳过任务栏、不在 Alt+Tab 出现。
- 拖动移动 + 边缘吸附 + 记忆位置 + 多显示器支持；可选"锁定位置"。
- 透明度可调；**点击穿透**开关（配合透明度，让悬浮窗不挡操作）+ 全局热键一键切换。
- 全屏应用/专注助手/游戏时自动隐藏（避免遮挡视频全屏），回桌面自动恢复。
- 收起/展开两种形态；悬停展开；空闲 N 秒半透明。

**条目操作**：单击复选框=完成；悬停显示"推迟（明天/1h）/详情"；双击=打开主窗口定位；右键=更多（编辑、等待他人、删除）。
**创建入口**：⚠️ 建议在悬浮窗内做**内联迷你输入**（点 ＋ 原地展开一个输入条），而不是跳到主窗口——跳转=中断，与"零决策"冲突。主窗口仍保留完整创建页。

## 6. 主窗口：页面地图、导航与按钮

```
┌────────────────────────────────────────────────────────────┐
│ 顶栏：搜索 / 命令面板 Ctrl+K        [＋ 新建（说/写）]      │
├────────┬───────────────────────────────────────────────────┤
│ 侧边栏  │  内容区                                            │
│ 今日    │  ┌────────────────────────────┐   ┌───────────┐  │
│ 收件箱  │  │ 列表（分组：逾期/今天/以后）  │   │ 详情抽屉   │  │
│ 全部    │  │  ☐ 与张总开会   15:00      │   │ 标题/时间  │  │
│ 已完成  │  │  ☐ 买牛奶                 │   │ 重复/标签  │  │
│ 悬浮窗  │  │  ...                      │   │ 原文/假设  │  │
│ 设置    │  └────────────────────────────┘   └───────────┘  │
└────────┴───────────────────────────────────────────────────┘
```

- **今日**（默认）：日期 + 三段分组（逾期 / 今天 / 无日期折叠）+ 行内快捷添加 + 顶部"一句话创建"输入条（可语音）。
- **收件箱**：AI 没把握 / 无日期的事项；顶部批量条（安排今天/明天、删除）；每条带 ✨ 或低置信度标记。
- **全部**：搜索 + 时间分组 + 标签筛选；只做列表，不做看板。
- **已完成**：24h 内完成记录，倒计时提示；恢复/清空。
- **悬浮窗**：实时预览 + 模式/行为配置（见 §5）。
- **设置**：
  - 通用：主题（浅/深/跟随）、开机启动、托盘行为、快捷键、语言、更新
  - 语音与 AI：麦克风设备、语言（中文/中英混说）、ASR 模型、LLM 模型、默认时间规则（"明天"默认 09:00 还是全天）、模型下载/卸载、GPU 开关、空闲卸载
  - 数据：存储路径、导出（JSON/Markdown）、导入、备份、回收站、清空、隐私说明（不留音频）
  - 关于：版本、更新、开源许可证
- **首次运行**（3 分钟）：欢迎 → 下载模型（一键，轻量/标准两档）→ 设快捷键 → 试说一句 → 完成。
- **快捷键**：`Ctrl+Alt+Space` 捕捉、`Ctrl+Alt+W` 显示/隐藏悬浮窗、`Ctrl+Alt+O` 主窗口、`Ctrl+K` 命令面板、列表内 `Enter` 详情 / `D` 推迟明天 / `Del` 删除 / `Esc` 关闭。

## 7. AI 契约（这是整个 AI 部分唯一需要严格定义的接口）

### 7.1 输入

- `transcript`：ASR 最终文本
- `now`：当前本地时间 + 时区（相对时间解析必需）
- `user_prefs`：默认时间规则（如"明天"= 09:00 / 全天、"下周"从周几开始）、常用标签、已有清单
- 输出必须是**严格 JSON**（llama.cpp grammar / JSON Schema 约束解码，避免"AI 说废话"）

### 7.2 输出 Schema（草案）

```json
{
  "items": [
    {
      "title": "和张总开会",
      "notes": null,
      "due": { "kind": "datetime", "at": "2026-11-02T15:00:00+08:00" },
      "remind": { "kind": "before", "minutes": 10 },
      "recurrence": null,
      "tags": ["工作"],
      "waiting_for": null,
      "confidence": 0.93,
      "assumptions": ["未说明日期，默认明天", "未说明时长，默认 1 小时"],
      "needs_review": false
    },
    {
      "title": "买牛奶",
      "notes": null,
      "due": { "kind": "none", "at": null },
      "recurrence": null,
      "confidence": 0.55,
      "assumptions": ["没有时间线索，放入收件箱"],
      "needs_review": true
    }
  ],
  "language": "zh",
  "split_reason": "两件独立的事，用逗号连接"
}
```

**硬规则**：
- 没有时间线索就 `due.kind = "none"`，绝不编时间；有疑问给低 `confidence` + `needs_review`。
- 多意图用逗号/换行/连词拆分；拆不动就一条（宁可少拆，不要乱拆）。
- 相对时间必须结合 `now` 与时区解析（"下周三"、"半小时后"、"月底"）。
- 输出只含 schema 字段；解析失败/超时 → 丢弃解析结果，用原文。

### 7.3 评估集（开发前就建）

- 50~100 条真实中文口语句子（覆盖：无时间、相对时间、绝对时间、"下周"、重复、多件事、中英混说、方言口音、噪声）。
- 指标：时间字段准确率（必须 ≥95% 才算可用）、拆分正确率、标题保真度、幻觉率（0）。
- 这是"AI 好不好"唯一可信的度量；没有它就会一直"感觉还行"。

## 8. 技术选型（初稿，待研究员校正）

> 结论先行：**Tauri 2 + Rust 核心 + React 前端 + 端侧 AI（sherpa-onnx + llama.cpp）**，全部进程内，无本地服务器、无 Ollama 依赖。

```
┌────────────────────────── Clarify.exe (Tauri 2) ──────────────────────────┐
│  WebView2: 主窗口(React) + 悬浮窗(React, 独立 WebviewWindow)               │
│      │ IPC (tauri commands / events)                                      │
│  Rust 核心：                                                              │
│   ├─ db (rusqlite + migrations, WAL)  ── tasks / completions / settings   │
│   ├─ capture (cpal 录音 + silero VAD)                                     │
│   ├─ asr (sherpa-onnx, 流式中英)                                          │
│   ├─ parser (llama.cpp + Qwen3-4B/1.7B GGUF, JSON grammar)                │
│   ├─ scheduler (提醒/24h 归档/开机自启)                                    │
│   └─ window/tray/shortcut/notification (Tauri 官方插件)                    │
│  models/ (首次下载，存 AppData)                                            │
└───────────────────────────────────────────────────────────────────────────┘
```

### 8.1 选型理由与备选

| 层 | 推荐 | 理由 | 备选 |
|---|---|---|---|
| 桌面壳 | **Tauri 2** | 安装包小（~10MB）、常驻内存低、原生 Rust 集成 AI、跨平台留门 | Electron（生态成熟/透明窗更稳，但 +400MB 内存、+100MB 包）；纯 WinUI（开发慢） |
| 前端 | React 19 + TS + Vite + Tailwind v4 + shadcn/ui + Zustand + Motion | 组件生态、悬浮窗可独立入口、动效成熟 | Svelte（更小但生态弱） |
| 本地 ASR | **sherpa-onnx**（SenseVoiceSmall / Paraformer，int8） | CPU 快、中文强、流式、Rust 绑定、Apache-2.0 | whisper.cpp（多语准、CPU 慢）；faster-whisper（需 Python） |
| 本地 LLM | **llama.cpp**（Rust `llama-cpp-2`）加载 Qwen3 系列 GGUF | 进程内、无服务、grammar 约束 JSON、GPU offload | Ollama（需用户安装，违背"免配置"）；云端 API（违背本地） |
| 模型 | ASR ~230MB；LLM 轻量 1.7B（~1.1GB）/ 标准 4B（~2.5GB） | 16GB 内存可跑；有 GPU 走 CUDA 加速 | 纯规则解析（快但覆盖差，作兜底） |
| 数据 | SQLite（rusqlite）+ 每日备份快照 | 单文件、可导出、零运维 | JSON 文件（简单但易损） |
| 原生能力 | 官方插件：global-shortcut / tray / notification / autostart / single-instance / window-state / positioner / updater | 少造轮子 | 自写 Win32（不必要） |

### 8.2 关键取舍（⚠️ 需要你确认）

1. **Rust 学习成本**：Tauri 的核心逻辑（DB/录音/AI 调度）建议用 Rust 写。如果你不熟 Rust，这一步会显著拖慢进度；替代方案是先用 Electron 快速验证产品，再迁 Tauri。**这取决于你的开发经验**。
2. **"完全本地"的代价**：模型下载 1~3GB、CPU 机器解析 3~8s、安装包/磁盘占用。如果接受"允许用户配置自己的 API Key（可选）"，可以极大降低低端机门槛——但与理念冲突，建议 v1 不做。
3. **透明悬浮窗**：Windows 上 Tauri 的透明/acrylic 有已知限制，需要 spike 验证；若体验不达标，降级为"纯色圆角卡片"（其实更符合极简审美）。

### 8.3 资源与延迟预算（验收标准）

| 指标 | 目标 |
|---|---|
| 热键 → 捕捉条出现 | < 150 ms |
| 说话停止 → 最终转写 | < 1.5 s（10s 语音） |
| 停止 → 草稿卡出现 | < 300 ms（乐观 UI，不依赖 AI） |
| LLM 结构化解析（后台） | 有 GPU < 3 s；CPU < 8 s（4B），1.7B < 5 s |
| 空闲常驻内存（模型卸载） | < 250 MB |
| AI 加载时峰值内存 | < 4.5 GB |
| 冷启动到托盘可用 | < 3 s |
| 安装包 | < 30 MB（模型另下载） |

> 这些数字必须用一次"技术尖峰"在真实机器（以及一台无独显的 16GB 机器）上实测，不能拍脑袋。见 §10。

## 9. 非功能需求

- **隐私**：默认不留音频；无网络请求（除模型下载/可选更新检查）；数据目录可迁移；无遥测。
- **可靠性**：SQLite WAL + 每日快照（保留 7 天）；崩溃恢复；录音中崩溃保留临时文本。
- **可维护**：解析器/模型可替换（接口隔离）；migration 版本化；解析评估集 + Rust 单测。
- **分发**：Windows NSIS/MSI 安装包；代码签名（SmartScreen 信任）；v1 内测阶段可先不签名但需提示。
- **可访问性**：全键盘操作、快捷键可改、高对比度、字号缩放（次级优先级）。

   - 全局热键 + 托盘 + 开机自启

   - llama.cpp + Qwen3 + JSON grammar 解析（测 tokens/s + 准确率）
   - 产出：一份实测数字 + Demo 录屏。**如果这四项都过，项目 80% 的技术风险就没了。**

### Phase 4（W6）M4 打磨

## 11. ⚠️ 需要你拍板的问题（按重要性排序）

1. **"自动解析安排"的边界**：A) 只解析出结构化字段（时间/重复/标题）——推荐；B) 解析 + 自动排进今天时间表（需要时长估计）；C) B + AI 每日规划建议。选 A 的话 v1 范围可控，B/C 是 v2 的独立大功能。
2. **24h 后"清除"**：A) 软归档可恢复（推荐，30 天）；B) 直接删除；C) 永久保留（与"清晰"冲突）。
3. **平台/分发**：A) 只 Windows 自用（最快）；B) Windows + macOS 发布；C) 要商业化/上架。→ 决定签名、更新、隐私政策成本。
4. **技术栈与你的经验**：Tauri/Rust 还是 Electron/TS？（取决于你熟什么，我不希望你卡在 Rust 上。）
5. **捕捉入口**：A) 悬浮窗内联迷你输入（推荐，少一次跳转）；B) 跳主窗口创建页（你原设想）。
6. **清单/标签**：v1 完全不分类（推荐先这样）/ 只做标签 / 要自定义清单？（影响数据模型。）
7. **模型策略**：默认下载哪档？轻量（1.7B，CPU 4~6s）还是标准（4B，GPU 2~3s）？是否接受首次 1~3GB 下载？
8. **视觉风格**：A) 纸张感极简（Things/Amie 风，推荐）；B) 信息密度高的效率工具（Notion/Linear 风）。
9. **提醒功能**：v1 是否必须（到点通知 + 睡眠补发）？还是"只做当日清单"？提醒是保持用户粘性的关键，但也会增加复杂度。

## 12. 你还没考虑、但会影响成败的事（遗漏清单）

1. **数据丢失 = 产品死亡**：本地优先没有云端兜底，必须做自动备份 + 导出 + 回收站；"24h 自动删除"必须软删。
2. **首次体验的 3 分钟**：下载 1~3GB 模型与"打开即用"矛盾，需要进度、两档模型、可离线安装包（U 盘/内置轻量模型）。
3. **AI 解析评估集**：不建 50+ 条真实中文语料，AI 质量永远靠感觉；这是最容易省掉、又最该先做的事。
4. **提醒可靠性**：应用关闭/睡眠/关机期间无法触发；要开机自启 + 托盘常驻 + 补发 + 首次说明预期。
5. **命名/商标**：Clarify 已被多家 CRM/软件使用，若公开分发需查商标；可先用内部代号，起名可另议。
6. **多显示器/高 DPI/虚拟桌面/全屏应用**：悬浮窗在这些场景的行为要逐个测，否则会显得"廉价"。
7. **重复任务 × 24h 清空 × 撤销** 三者交互是状态机最容易出 bug 的地方，先写测试用例。
8. **解析歧义的产品化**：无日期 ≠ 忘了，可能真的"有空再说"；"下周"从周几算；跨天边说"今晚"。默认规则要可设置。
9. **隐私承诺要可验证**：不留音频、无遥测——需要在设置里写清楚，并且代码里真的不联网。
10. **Windows 签名/SmartScreen**：不签名会有"未知发布者"警告，影响分发信任；证书要花钱（约 ¥1-3k/年），提前决定。
11. **迁移**：用户已有滴答/Todoist 数据怎么办？v1 可不做，但要说明。
12. **同步**：v1 不做，但 schema 预留 `updated_at/device_id`，未来可用文件快照同步（iCloud/OneDrive），避免推倒重来。
13. **电池/噪音**：笔记本上 LLM 常驻会耗电/风扇响；必须空闲卸载 + 可选"仅插电时用大模型"。
14. **崩溃恢复**：录音中崩溃不能丢输入（临时文件）。
15. **度量**：从第一天记录匿名本地指标（捕捉耗时、解析失败率——只存本地供自己看），否则无法迭代。
16. **重复/误触**：连按热键、重复口述同一件事 → 去重策略（同标题 10 分钟内合并提示，不自动合并）。
17. **空状态与引导**：新用户第一次打开看到什么？"说一句试试"比空白列表重要。
18. **可测试的验收标准**：每个里程碑定义"能做什么"，而不是"写完了"。
